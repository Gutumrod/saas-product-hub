# LK01 WSTERA Link ΓÇö Independent Product Expert Answer

## 1. Recommendation

**What it should be:** WSTERA Link should be exactly what its locked baseline defines ΓÇö a branded campaign-link and first-party click-attribution SaaS for Thai online sellers and creators, whose differentiating promise is a *stable branded short link/QR whose destination can be switched after distribution*, paired with lightweight source-attribution analytics. It must not drift into generic URL shortening, a web-analytics replacement, or a marketing suite (`docs/00_PRODUCT_VISION.md`).

**For whom:** First primary segment = **Thai online sellers operating across Facebook, LINE, TikTok, and Shopee/Lazada affiliate links or printed/QR materials** (`00_PRODUCT_VISION.md`, Primary ICP #1), with creators/affiliate operators as the second segment. The design already reflects this: PromptPay manual-renewal rail (ADR-001), mobile-first dashboard (`06_UX_USER_FLOWS.md`, UX Rules), Asia/Bangkok default display timezone (`05_ANALYTICS_SPEC.md`).

**Where V1 ends before implementation:** V1 ends at the **Free-tier core loop implemented to production quality** ΓÇö signup ΓåÆ tenant ΓåÆ create link ΓåÆ copy/QR ΓåÆ redirect ΓåÆ first tracked click ΓåÆ analytics view ΓÇö plus the metering/quota and entitlement machinery needed to sell it. Concretely: Roadmap Phases 0ΓÇô4 are the V1 build core (link/redirect, analytics/quota, billing via centralized billing-core); **campaigns, UTM builder, custom domains, CSV export, API/webhooks, and team access are explicitly Phase 5, not V1 scope** (`docs/07_DEVELOPMENT_ROADMAP.md`; `01_PRD.md` FR-PAID-001/002). The non-goals list in the Vision doc stands: no analytics-suite replacement, no ad-platform pixel/attribution replacement, no link-in-bio builder, no A/B testing engine, no identity resolution, no enterprise SSO. Implementation stays on hold per `docs/CURRENT_STATUS.md` until portfolio P0b/P1 gates and the Phase P4 slot open; Phase 0 intake is the first action ΓÇö no code/schema before it.

**Identity beyond generic shortening:** the product is the *destination-switch + attribution loop*, not the shortener. The short URL is a stable handle (QR encodes the short URL, never the destination ΓÇö FR-LINK-006); the value is (a) knowing which channel sent the click and (b) repointing traffic without reprinting QR codes or republishing links.

## 3. Key reasons

1. **The pain is concrete and segment-specific.** Thai sellers distribute links/QR across Facebook/LINE/TikTok and physical materials; once published, they can neither be repointed nor attributed first-party. The vision's promise and JTBD #3/#4 target exactly that; nothing in the docs suggests the product is a commodity shortener.
2. **Destination-switching is the defensible core.** The whole redirect stack is designed around it: stable public URL (FR-LINK-004), versioned destination mutation with cache invalidation (FR-REDIRECT-004, Architecture "Link Resolution"), audit of every change (`03_DATA_SECURITY_TENANCY.md` Audit Required Actions). Attribution (which channel sent the click) is the second half of the same loop ΓÇö both are needed for the promise to hold.
3. **The smallest hot-path-safe V1 is well-defined and already sequenced.** Phases 2ΓÇô3 (link core + redirect Worker; analytics + quota) form the product's minimum useful core; Phase 4 billing is required to monetize; Phase 5 adds only paid-tier features. Free-tier scope (FR-Q-001 + FR-LINK + FR-REDIRECT + FR-AN) *is* the V1 product; everything Pro/Business is deliberately later.
4. **Redirect reliability outranks analytics completeness by design.** Background analytics emission, fail-safe (never fail-open to a guessed destination), no synchronous billing on the hot path, and the failure matrix all enforce the Vision's first product principle. This is the right ordering for a link users print on packaging.
5. **Vendored presence Γëá V1 necessity.** Of the 10 vendored copies, only `auth-supabase`, `tenant-context`, `rate-limit`, and `import-export` map to product-facing capability (identity/tenancy boundary, quota enforcement, export pipeline); `audit-log`, `config-runtime`, `health-check` are platform plumbing; `payment`/`subscription`/`webhook-receiver` are explicitly de-authoritized by the centralized billing-core decision. Meanwhile the genuinely product-defining pieces (link schema, redirect Worker, analytics pipeline) are product-owned code ΓÇö so no vendored module can be cited as proof a V1 capability must exist.
6. **Minimum analytics is sufficient and honest.** Totals + source breakdown + recent trend + date range, with UTMΓåÆreferrerΓåÆDirect precedence and no unique-visitor claims, is exactly enough to answer the owner's question "which channel should I spend effort on" (JTBD #5) without over-claiming against ad-platform counters (`05_ANALYTICS_SPEC.md` reconciliation caveat).
7. **Success criteria are measurable pre-launch.** Activation (first link + first tracked click), North Star (active tracked links receiving real clicks), redirect success rate, and the phase-gate regime give an objective "is V1 working" test that doesn't depend on vanity traffic.

## 4. Risks/failure cases

- **Free-tier analytics blindness at limit:** at 250 tracked clicks/month the links keep working but the customer's evidence stream stops ΓÇö the product's own core value pauses. Mitigation exists (06_UX warning flow, upgrade CTA must not imply broken links) but copy/UX must be enforced in build, or churn/confusion follows.
- **Stale destination after a switch:** if cache invalidation lags, a seller's "switch the campaign" action silently sends traffic to the old offer ΓÇö the single most damaging failure for the differentiating promise. FR-REDIRECT-004 and the version/purge/TTL policy bound it, but this is unproven pre-build and is a Phase 2 gate item.
- **Fail-safe Γëá always-available:** on Supabase lookup failure with cache miss, the design refuses to guess a destination (fail closed). Correct policy, but it means redirects can fail outright in an outage; redirect-reliability marketing claims must be tempered accordingly.
- **Attribution-expectation gap:** sellers comparing dashboard numbers to Facebook/TikTok/LINE counters will see mismatches (bot/preview/attribution definitions). The product must never promise parity (`05_ANALYTICS_SPEC.md`); otherwise support load and distrust follow.
- **PromptPay renewal cliff:** manual rail means every period is a renewal decision; expiry ΓåÆ 3-day grace ΓåÆ Free enforcement is a designed churn point. Reminders and `paid_through` visibility are specified; the risk is operational (reminder delivery/verification), and reconciliation must exist before PromptPay release (hard preflight).
- **Entitlement snapshot staleness:** bounded local snapshot keeps the redirect hot path clean, but control-plane features may briefly diverge from provider truth during billing-core outage; the failure matrix covers it, but tests must prove no unverified upgrade and no wrongful lockout.
- **"1 lifetime destination change per link" on Free:** the paid unlimited-edits hook is a monetization lever, but if a free seller's core need *is* repeated repointing, one change may feel like a paywall on the product's headline promise ΓÇö worth watching in Beta conversion signals rather than changing now (change requires ADR).
- **Hold discipline:** P0a-C1 PASS does not unlock implementation (`WORK-BRIEF-2026-09-03.md` stop conditions); building early against an unfixed portfolio billing-core contract would force rework.
