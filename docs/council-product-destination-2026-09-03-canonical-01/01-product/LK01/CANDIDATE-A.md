# LK01 WSTERA Link — Product Gate Expert Answer 

Gate question: What exactly should WSTERA Link be, for whom, and where does V1 end before implementation?
Frozen brief: `COUNCIL-BRIEF.md`. This is an independent Council expert output. No gate verdict, no pricing/competitive positioning, no product-destination revival of SU01, no code/schema/Phase0/deploy/module changes.

## Recommendation

WSTERA Link should be a **branded campaign-link and click-attribution SaaS for Thai online sellers, creators/affiliate operators, agencies/social admins, and small businesses** — explicitly NOT a generic URL shortener. Its identity and defensible value loop is: **a stable public link/QR whose destination can be changed after distribution without re-printing, paired with first-party outbound click attribution that gives a business owner channel-level evidence of where customer traffic comes from.** The core product promise (from `00_PRODUCT_VISION.md` and `PRODUCT_DECISIONS.md`): "Create a stable branded link, know which channel sends customers, and change the destination without replacing published links or QR codes."

I recommend that V1 be scoped to the destination-switching + attribution value loop only, with the free tier demonstrating value and paid value centered on custom domain, campaign analytics, higher limits, export/API/team (per product principles and FR-PAID). V1 must be built as a multi-tenant, Cloudflare-first TypeScript product (links dashboard on `links.wstera.com`, redirect edge on `go.wstera.com`), with Supabase Postgres/RLS as authoritative store and Cloudflare cache as performance-only. Per `CURRENT_STATUS.md`, implementation is currently on HOLD pending portfolio-level P0b repository-readiness and P1 shared-boundary/billing-contract gates, and must not begin ahead of Phase 0 intake.

For V1 the product-defining capabilities are: (1) link core with versioned destination mutation + QR encoding the stable URL, (2) the redirect edge that resolves fast and fails safely, (3) attribution analytics (UTM/referrer/bot-filtered tracked clicks) with plan-based quota and retention, and (4) tenant isolation/RLS as the trust foundation. Vendored billing modules remain reference-only after the centralized billing-core decision.

## Key reasons

1. **Primary user & core pain.** First primary segment is Thai online sellers/creators operating across Facebook, LINE, TikTok, Shopee/Lazada affiliate links, and printed QR. Core pain = they publish a link/QR, it goes out into the wild, and they cannot (a) tell which channel actually sent customers, or (b) fix/redirect a destination once printed/share is live. WSTERA Link answers that specific pain: a stable URL that survives a destination change plus channel attribution. This is a real JTBD the generic-shortener framing does not own.
2. **Product identity is destination-switching + attribution, not short URLs.** The value loop is: create stable branded link/QR → distribute → track first-party outbound clicks (UTM→referrer→direct precedence, bot-filtered) → change destination without reprinting → attribute traffic by channel/campaign to decide where effort goes. Shortening is the commodity wrapper; switching + attribution is the differentiator and moat.
3. **Smallest hot-path-safe V1.** The minimum coherent V1 = Phase 1 (auth/tenant/RLS) + Phase 2 (link core + redirect edge + QR) + Phase 3 (analytics + quota), all of which are the free-tier value demonstration and the platform trust foundation. Phase 4 (billing) gates monetization; Phases 5–6 (paid features + hardening) extend it. The redirect hot path has no synchronous analytics or billing dependency (NFR-REL-001, FR-REDIRECT-003, architecture failure matrix), so V1's core value loop is independently hot-path-safe and fail-closed.
4. **Minimum analytics for usefulness** = tracked-clicks attribution with UTM/referrer source breakdown, daily aggregates, plan-quota enforcement that never blocks the redirect, and deterministic bot filtering — enough for "which channel sends customers" evidence. It deliberately does NOT claim unique visitors or raw IP, avoiding the identity/privacy weight that would balloon V1 scope.
5. **Product-defining vs platform plumbing.** Product-defining = link mutation/versioning + QR stability, redirect resolution/fail-safe + cache-version propagation, attribution normalization + quota algorithm, and tenant isolation/RLS (the trust contract without which attribution is meaningless). Platform plumbing = rate-limit (host must inject a real shared store anyway; memory adapter is single-process-only), config-runtime, health-check, audit-log, import-export adapter, tenant-context/auth-supabase helpers — reusable infra that is not the differentiator. The billing modules (subscription/payment/webhook-receiver) are explicitly reference-only post centralized billing-core. Vendored presence does not make any module V1-necessitating; necessity is driven by PRD functions, not copy location.
6. **Clear cut line / non-goals.** V1 explicitly excludes full web analytics, ad-platform attribution or pixel replacement, link-in-bio, marketing automation, A/B testing, deep identity resolution/cross-device tracking, and enterprise SSO/SAML. These are the "where V1 ends" boundary. Every phase has a blocking gate and no phase starts before the previous gate passes.

## Risks/failure cases

- **Billing/Payment complexity risk:** PromptPay manual renewal with reconciliation mandates (FR-BILL-008, Money Gate) is the heaviest non-core risk. Failure cases: entitlement granted without verified provider truth; duplicate/replayed/out-of-order events double-extending period; reconciliation missing at PromptPay activation. The architecture mitigates by keeping billing off the redirect hot path and using a local entitlement snapshot, but the Money Gate dependency is a real schedule/quality risk and is a portfolio-shared gate LK01 cannot close alone (CURRENT_STATUS).
- **Attribution credibility risk:** Dashboard numbers may differ from Facebook/TikTok/LINE because bot/preview/attribution definitions differ. If product copy overclaims parity, trust erodes. Must keep the reconciliation caveat visible.
- **Redirect reliability/edge risk:** Destination-change propagation depends on cache/version/TTL invalidation predictability (FR-REDIRECT-004). Stale routes could serve an old destination; cache-miss + Supabase unavailable must fail safely (never guess destination). The hot path must stay bounded and monitored.
- **Multi-tenancy/isolation breach** would be existential — any cross-tenant read/write/export/inference is a hard failure (FR-TENANT-003, Security Gate). RLS is required before any feature release (NFR-SEC-001).
- **Free-tier abuse / spam links:** public-branded link infrastructure is abused for phishing/spam. Reserved/unsafe slug + destination validation (FR-LINK-002/005) and deterministic bot/spam controls are needed; undefined abuse thresholds are a gap.
- **Vendor dependency drift:** Cloudflare for SaaS custom-hostname limits and Stripe Thailand eligibility/cost can change; docs mandate re-verification before the consuming phase. Failure to re-verify risks a paid feature or billing rail not actually available.
- **Scope creep into paid features (Phases 5) before the core loop is solid,** or conversely shipping billing (Phase 4) before P1 usage-model boundary. Change rule requires ADR + doc update before any adaptation.
- **Unique-visitor temptation:** pressure to add unique visitor/fingerprinting would conflict with the privacy baseline and expand scope; must hold the line.
