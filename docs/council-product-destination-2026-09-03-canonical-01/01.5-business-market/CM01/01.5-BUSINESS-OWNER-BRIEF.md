# CM01 Business / Market Owner Brief

รอบนี้ประชุมเรื่อง Business / Market Gate ของ **CM01 Booking Claim & Case Mgmt**: สร้างแล้วขายได้ไหม ใครจ่าย เพราะอะไร และติดอะไรจริงก่อนขาย

## สรุปสั้น

CM01 มีทิศทางขายได้แบบมีเงื่อนไข แต่ยัง **ไม่ PASS**.

Gate ทางการคือ **REMEDIATE**, confidence **59/100**. เหตุผลเดียวที่ยังเป็น blocker ของ Business / Market Gate คือ **OD-001 License Strategy**: ตอนนี้ repo เป็น MIT ซึ่งเปิดให้คนเอาโค้ดไป copy, modify, distribute, sublicense, resell ได้ แต่โมเดลที่คิดไว้คือขาย source code แบบ paid single-use. สองอย่างนี้ชนกันตรง ๆ ก่อนขายจริง

## CM01 ขายอะไร

CM01 ขาย **source code React template/module** สำหรับหน้าจอจัดการเคส/เคลม/งานหลังบ้านแบบ Thai-first ให้ **frontend developer หรือ web agency** เอาไป embed ในงานลูกค้าของตัวเอง

สิ่งที่ขายไม่ใช่ SaaS, ไม่ใช่ backend, ไม่ใช่ระบบ ticket เต็มตัว, และไม่ใช่ฟีเจอร์ของ BK01.

V1 ที่ล็อกไว้คือ local-first:

- มีหน้า intake, ticket detail/action, history/retention
- เก็บข้อมูลด้วย `localStorage`
- มี `TicketRepository` เป็น boundary สำหรับต่อ adapter ภายหลัง
- ไม่มี auth
- ไม่มี backend
- ไม่มี multi-user sync

คนจ่ายเงินคือ dev/agency. คนใช้ปลายทางคือเจ้าหน้าที่ดูแลเคสในธุรกิจของลูกค้าเขา

## ทำไม backend absence ไม่ใช่ blocker

ผู้เชี่ยวชาญ 3/3 เห็นตรงกันว่า backend ไม่ใช่ตัวบล็อกของ V1 เพราะ CM01 ไม่ได้ถูกขายเป็น production SaaS ตั้งแต่แรก. มันถูกวางเป็น source template ที่ใช้ local-first และบอกตรง ๆ ว่า BYO backend / adapter เป็นเรื่องหลัง V1

ถ้าเราไปบังคับว่าต้องมี backend ก่อนถึงขายได้ เราจะเปลี่ยนประเภทสินค้าเองจาก template/source product ไปเป็น SaaS/runtime product ซึ่งขัดกับ Product Gate ที่ล็อกไว้แล้ว

ดังนั้น backend adapter ยังเป็นเรื่องที่ต้องตัดสินทีหลังใน OD-004 แต่ไม่ใช่ blocker ของ Business / Market Gate รอบนี้

## ทำไม license เป็น blocker

License เป็น blocker เพราะมันกระทบวิธีเก็บเงินโดยตรง

ตอนนี้ license เป็น MIT. ถ้าขาย source code ภายใต้ MIT แล้วตั้งใจจำกัดว่า "single-use" หรือห้าม resale แบบ commercial template ปกติ มันขัดกันเอง เพราะ MIT อนุญาตให้ redistribution/resale ได้กว้างมาก

ถ้าไม่แก้เรื่องนี้ก่อน sale:

- buyer คนแรกอาจเอาโค้ดไปแจกหรือขายต่อได้ตามสิทธิ MIT
- โมเดล paid single-use เสียฐานทาง commercial
- pricing/package/support/refund เขียนให้ชัดไม่ได้
- Gate จะกลายเป็น PASS แบบหลอกตัวเอง ทั้งที่ตัว blocker จริงยังอยู่

## สิ่งที่ผู้เชี่ยวชาญเห็นตรงกัน

- **3/3** CM01 เป็น Thai-first local-first React source template/module
- **3/3** payer คือ frontend developer หรือ web agency
- **3/3** backend absence ไม่ใช่ blocker ของ V1
- **3/3** OD-001 license conflict เป็น blocker จริงก่อนขาย
- **3/3** buyer demand และ willingness-to-pay ยังไม่ได้พิสูจน์
- **3/3** pricing/packaging ยังไม่ final

### Decision D1 — จะจัดการ license สำหรับ paid source distribution อย่างไร

- Status: REQUIRED
- Council recommendation: Option A
- Council support: 3/3 that the contradiction is real and must be resolved before sale
- Confidence: 59%

### Option A — Replace/augment sale package with commercial EULA or dual-license terms before first sale

- ข้อดี: ทำให้โมเดล paid single-use/source distribution ไม่ชนกับ MIT แบบเดิม และเขียนสิทธิการใช้/แจกต่อ/support ได้ชัด
- ข้อเสีย: ต้องทำงานด้าน license/EULA เพิ่ม และอาจต้องให้คนที่เข้าใจกฎหมายช่วย review
- ผลต่อระบบ: ไม่ต้องแก้ product code หรือ backend จาก decision นี้โดยตรง แต่ต้องทำให้ sale package/license artifact ตรงกับสิทธิที่ขาย
- ผลต่อรายได้/ต้นทุน: รองรับการขาย source package ได้ชัดกว่า แต่มีต้นทุนทำเอกสาร/นโยบาย license
- ความเสี่ยง: ถ้าเขียน license ไม่รัดกุม อาจยังเกิด dispute หรือ buyer เข้าใจสิทธิผิด

### Option B — Keep MIT and sell only convenience/support, accepting redistribution risk

- ข้อดี: ไม่ต้องเปลี่ยน license เดิม และเปิด friction ต่ำกับ developer ที่ชอบ MIT
- ข้อเสีย: ขายแบบ single-use/source restriction ไม่ได้จริง ต้องยอมรับว่า buyer redistribute/resell ได้ตาม MIT
- ผลต่อระบบ: ไม่ต้องแก้ product code หรือ license structure มาก แต่ต้องเปลี่ยน packaging/copy ให้ขาย convenience/support ไม่ใช่สิทธิ exclusive/single-use
- ผลต่อรายได้/ต้นทุน: รายได้อาจอ่อนกว่าเพราะตัว source ถูกแจกต่อได้ ต้องหาเงินจาก support, update, convenience, หรือบริการเสริม
- ความเสี่ยง: ตลาดอาจ copy/redistribute เร็ว และราคา source package อาจป้องกันยาก

### Option C — Delay sale until legal/licensing review produces a final policy

- ข้อดี: ลดความเสี่ยงตัดสิน license ผิด และให้ policy ชัดก่อนแตะ commercialization
- ข้อเสีย: ชะลอการขายและ packaging ทั้งหมด
- ผลต่อระบบ: ไม่มี product code/backend change ตอนนี้ งาน commercial หยุดรอ policy
- ผลต่อรายได้/ต้นทุน: เลื่อนรายได้ แต่ลดโอกาสเกิดปัญหา license หลังขาย
- ความเสี่ยง: ถ้ารอนานเกินไป CM01 อาจค้างเป็น prototype และเสีย momentum การ validate buyer

## สิ่งที่ยังไม่รู้ / ยังไม่ตัดสิน

- OD-002 buyer demand: ยังไม่มี buyer interview, paid pilot, pre-order, LOI, conversion evidence หรือ channel proof
- Willingness-to-pay เทียบกับ generic React/admin templates ยังไม่พิสูจน์
- Final pricing/packaging ยังไม่ approved
- OD-006 buyer docs/support ยังไม่ครบ: embed guide, adapter guide, theme guide, limitations, distribution manifest, support scope
- OD-004 backend adapter ยังเป็น post-V1 และยังไม่เลือกว่าจะไป Supabase, REST, Module Hub `ticket-tracker`, หรือทางอื่น
- Unit economics, support burden, dev-days saved, localization hours avoided, cross-browser support, repeat purchase, retention ยังต้องพิสูจน์

## Gate Status

**Business / Market Gate = REMEDIATE**

แปลว่า: ทิศทางตลาดยังไม่ตาย และไม่ใช่ BLOCK แต่ยังประกาศ PASS ไม่ได้จนกว่า Owner จะเลือก OD-001 แล้วเอกสาร remediation ถูก persist ให้สอดคล้องกับ decision นั้น
