2. Verdict

กูให้ REMEDIATE ไม่ใช่ PASS และไม่ใช่ BLOCK

เหตุผลคือ 3/3 candidate เห็นตรงกันว่า payer, pain, wedge, และ monetization direction มีเหตุผลพอไปต่อ แต่ยังไม่มีหลักฐานตรงจาก owner-operator ไทย, ยังไม่รู้ qualified beachhead จริง, ยังไม่รู้ ARPU จริง, และยังไม่รู้ onboarding cost จริง

นี่ไม่ใช่ technical blocker และไม่ใช่ให้ไป build เต็มทันที สิ่งที่ต้องทำต่อคือ validation เชิง Business/Market แบบแคบและมีหลักฐาน

3. Initial payer / beachhead

ผู้จ่ายเงินเริ่มต้นที่ชัดที่สุดคือ เจ้าของหรือทีม ops/admin ของ importer/distributor ไม่ใช่ dealer และไม่ใช่ supplier/factory

Beachhead ที่ควรเริ่มคือธุรกิจไทยขนาดเล็กถึงกลางที่มี:

  • dealer/reseller ประมาณ 20-200 ราย
  • SKU/variant หลายรายการ จน allocation ไม่ใช่เรื่องง่าย
  • เจอ partial supply, factory delay, quota, หรือ shortage ซ้ำๆ
  • ใช้ Excel/Google Sheets + LINE/chat + ความจำของเจ้าของหรือแอดมิน
  • เคยมีปัญหา oversell, shortage รู้ช้า, dealer ถามว่าทำไมไม่ได้ของ, backorder งง, หรือไฟล์ Excel ทับกัน

ห้ามตีความว่า importer ทุกเจ้าคือลูกค้า ถ้า supply เหลือๆ หรือ dealer น้อยมาก WSM ไม่มี hook พอให้จ่ายรายเดือน

4. Recurring pain

Pain ที่น่า monetize คือ supply ไม่แน่นอนและต้องจัดสรรของให้ dealer แบบอธิบายได้

ปัญหาหลัก:

  • dealer ส่งคำขอใน LINE/chat กระจัดกระจาย
  • request ถูกเข้าใจผิดว่าเป็น order หรือ promise
  • factory order ถูกเข้าใจผิดว่าเป็น confirmed/received supply
  • shortage รู้ช้า
  • allocation ทำใน Excel หรือจากความจำเจ้าของ แล้วอธิบายย้อนหลังยาก
  • backorder ถูกลืมหรือ double count
  • dealer ต้องถาม admin ซ้ำๆ ว่าได้ของไหม
  • history หายเมื่อ spreadsheet ถูกแก้หรือทับ

มูลค่าทางธุรกิจ เช่น admin time saved, dispute reduction, allocation accuracy ยังเป็น hypothesis ต้องวัดใน pilot

5. Status quo / competitors

คู่แข่งตัวจริงคือ Excel + LINE/chat + owner memory เพราะฟรี คุ้นมือ และ flexible

คู่แข่ง adjacent:

  • Zort, Smith, Fusion และระบบ dealer/order ไทยอื่นๆ
  • FlowAccount/PEAK/accounting-POS SaaS ที่มี inventory บางส่วน
  • Odoo/ERP-lite
  • B2B ordering portals เช่น SparkLayer, OrderDock, B2B Wave, Brandboom, Shopify B2B
  • Inventory/OMS เช่น Zoho Inventory, inFlow, Unleashed, Cin7, Katana
  • Supply planning/enterprise systems เช่น Netstock, Oracle/SAP style fair-share allocation

WSM ไม่ควรสู้ด้วยการเป็น ERP หรือ order portal แต่ต้องยืนบน allocation truth: Demand -> Supply -> Gap -> Allocation -> Fulfillment

6. Differentiation wedge

Wedge ที่มีจริงคือ:

  • Ordered != Confirmed != Received
  • Requested != Allocated != Fulfilled
  • คำนวณ gap โดยไม่ double-subtract backorder
  • allocation แบบ manual/partial มี audit trail
  • backorder carry ต้อง explicit ไม่ auto
  • dealer เห็นผลของตัวเองโดยไม่ต้องถาม admin
  • history ไม่หายแบบ spreadsheet

ถ้าขายเป็น "spreadsheet ที่สวยขึ้น" หรือ "ระบบ order/ERP อีกตัว" wedge จะพัง

7. Monetization direction

Commercial values ยัง TBD ห้ามล็อกราคาสาธารณะในรอบนี้

ทิศทางที่ coherent:

  • subscription รายเดือน/รายปีต่อ tenant
  • tier หลักตาม active dealers เพราะ dealer count สัมพันธ์กับ workload และ allocation complexity
  • SKU/variant เป็น secondary tier ได้
  • seats ไม่ควรเป็นตัวคิดเงินหลัก เพราะทีมแรกๆ มีแค่ owner + admin 1-3 คน
  • onboarding/data-import fee ควรมี เพราะ Excel/SKU/dealer/supplier setup มีต้นทุนจริง
  • advanced allocation policy, automation, API/integration, audit export เป็น tier ต่อไป
  • ไม่ควรใช้ take-rate/transaction fee ใน V1

8. Sales / onboarding / delivery

Sales motion ที่เหมาะคือ owner-led demo + assisted onboarding

ไม่ควร pure self-serve เพราะ value แรกต้องเกิดจาก real round จริง ไม่ใช่แค่สมัครแล้วลองเล่นเอง และไม่ควร enterprise consulting เพราะ ICP จ่ายไม่ไหวถ้า onboarding หนักเกิน

Onboarding ที่ควรล็อก:

  • เริ่มจากรอบถัดไป ไม่ migrate history ลึกใน V1
  • import SKU/dealer/supplier จาก Excel template
  • สร้าง dealer code/link แบบ zero-install และ LINE-friendly
  • run รอบแรก parallel กับ Excel ได้
  • train admin เรื่อง state separation และ allocation logging

ถ้า onboarding กลายเป็นหลายสัปดาห์ มี custom ERP, integration, หรือ data cleanup หนักๆ unit economics จะเสี่ยงพัง

9. Risks / blockers / downstream split

Genuine Business/Market blockers

ยังไม่พบ fatal blocker ตอนนี้:

  • payer มีชัด
  • pain เกิดซ้ำได้จริงใน ICP ที่ถูกต้อง
  • wedge แยกจาก spreadsheet/ERP/order portal ได้
  • monetization direction coherent
  • beachhead แคบแต่พอใช้ validate ได้

Remediation required

ต้องแก้/พิสูจน์ก่อนเดินกว้าง:

  • เลือก first vertical หรือ acquisition segment ที่แคบกว่านี้
  • สัมภาษณ์ owner-operator 5-10 รายที่มี constrained supply + dealer allocation จริง
  • พิสูจน์ว่า pain เป็น top pain ไม่ใช่แค่ annoyance
  • พิสูจน์ว่าเขามอง WSM เป็น allocation truth/provenance ไม่ใช่ spreadsheet/order portal
  • ประเมิน onboarding effort จาก spreadsheet/dealer/supplier data จริง
  • ล็อก packaging dimensions โดยราคายัง TBD

Downstream preserved-not-blockers

สิ่งต่อไปนี้ยังไม่ใช่ blocker ของ gate นี้ แต่ต้องเก็บไป validate:

  • retention/churn จริง
  • CAC/conversion จริง
  • admin time saved จริง
  • dispute reduction จริง
  • allocation accuracy จริง
  • ARPU จริง
  • production billing
  • runtime/database placement
  • architecture/security
  • implementation/deployment

Decision D1 — เลือก first beachhead vertical สำหรับ validation รอบแรก

Decision required: เลือก first beachhead vertical สำหรับ validation รอบแรก

Recommended decision: เริ่มจาก vertical ที่มี recurring constrained supply + dealer allocation ชัดที่สุด เช่น auto parts/accessories, electronics/appliances, building materials/hardware, หรือ FMCG sub-distribution โดยเลือกหนึ่งเดียวก่อน ไม่เปิดกว้างทุก importer

Why: ถ้าไม่ narrow จะ validate ไม่เจอ pain ที่แท้จริง และ WSM จะถูกลากไปเป็น generic order/ERP tool

Options:

  • Approve: เลือกหนึ่ง vertical แล้วทำ discovery 5-10 owner calls
  • Revise: เสนอ vertical อื่นพร้อมเหตุผลเรื่อง recurring shortage/allocation
  • HOLD: หยุด Business/Market validation ไว้ก่อน

Decision D2 — ยืนยันว่า V1 validation จะไม่ lock final public prices

Decision required: ยืนยันว่า V1 validation จะไม่ lock final public prices

Recommended decision: อนุมัติให้ทดสอบเฉพาะ monetization structure: per-tenant subscription, active-dealer tier, optional SKU tier, onboarding/data-import fee; ราคาจริงยัง TBD

Why: brief ระบุชัดว่า commercial values ยัง TBD การเดาราคาใน gate นี้จะทำให้ source-of-truth เพี้ยน

Options:

  • Approve: validate structure โดยไม่ประกาศ final prices
  • Revise: เพิ่ม/ตัด billing dimensions ที่ต้องทดสอบ
  • HOLD: รอ owner กำหนด pricing policy ก่อน validation
