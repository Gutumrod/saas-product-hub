## 5. New finding — `F-GATE-RLS-COUPLING` (HIGH)

**The H3D acceptance gates cannot be executed by a least-privilege role.** This was
established empirically, not argued.

A purpose-made read-only role (`SELECT` on `ps01`, no superuser, no `BYPASSRLS`, no
write anywhere) was created and measured against LAB:

- **Check 1 can never pass.** The expected manifest embeds a data row,
  `ps01.commercial_packages WHERE id='starter'`, inside the fingerprint. That table
  has RLS enabled with exactly one policy, `commercial_packages_select_policy`,
  scoped to `{authenticated}`. Any role that respects RLS reads `row: null` and
  produces a different fingerprint. The first run reported
  `drift: ["starter_package row changed"]` with live fingerprint `d950f6d3…` — **a
  visibility artifact, not LAB drift**, proven because the only variable changed
  before it passed was `BYPASSRLS`.
- **Check 2a would have produced a false pass.** Of the 23 tables it counts, **12
  were RLS-blind** to that role, including `ps01.camera_access_audit`,
  `commercial_packages`, `shop_subscriptions`, `subscription_audit_log`,
  `camera_settings`, `room_rate_plans`, `import_batches` and `auth.users`. The
  baseline expects `0` for those tables and the role would have returned `0` for all
  of them — because it could not see them. Every zero would have read as green and
  proved nothing.

So a programme whose purpose is to enforce least privilege has acceptance gates that
are only satisfiable by a credential that bypasses privilege. That is an
architectural defect in the gate design, not in LAB and not in the role.

Intended fix, for its own unit with its own review: separate schema-drift capture
from RLS-protected data-row capture, so the drift gate can run under least privilege;
and make the count gate assert measurability before reporting a zero.

**Hard-gate before `H3D-LIVE`,** together with `F-CATALOG-PROVENANCE`.

   alternative it is far narrower: `postgres` writes to 14 schemas and is superuser;
   `h3d_ro + BYPASSRLS` reads everything and writes nothing.

   This is a decision to trade RLS-scoped read confinement for measurement validity,
   on an ephemeral role, for a read-only measurement. It is not a licence to reuse

### Correction — all three open findings block `H3D-A1`, not `H3D-LIVE`

§5 and §6 above placed the hard gate before `H3D-LIVE`, reasoning that it is "the
first stage where a wrong-target connection mutates data". **That reasoning is
wrong.** Reading the definition of acceptance gate A1 in
`BRIEF-CLAUDE-H3D-STATIC-ACCEPTANCE-REMEDIATION-2026-09-09.md`, `H3D-A1` is the
rollback-only / two-session concurrency and failure-injection validation. It issues
real DML in real transactions with real locks and rolls it back. Rolled back is not
the same as never written:

- a rollback against the **wrong database** still takes locks on live tables and can
  block real traffic while it runs;
- a rollback that fails partway leaves real rows;
- its own exit criterion — "must not leave committed PS01 fixture rows, Auth
  identities, runtime grants, hook changes, or unrelated state" — is a *counting*
  claim.

Each open finding therefore lands directly on `H3D-A1`:

| Finding | Why it blocks `H3D-A1` |
|---|---|
| `F-CATALOG-PROVENANCE` | Nothing can prove which database a capture came from, and `H3D-A1` is the first stage that writes. A wrong target here mutates rather than mislabels. |
| `F-GATE-RLS-COUPLING` | "We left nothing behind" is a count, and 12 of 23 counted tables are RLS-blind to a least-privilege role. The stage's own exit criterion cannot be evidenced. |
| `auth.users` unmeasurable | The criterion explicitly names Auth identities. `42501` means that specific claim cannot be proven at all. |

There is also a credential problem with no answer yet: `H3D-A1` needs `INSERT`/
`UPDATE`/`DELETE` on `ps01`, and §8 established that no least-privilege writable
credential exists — only the `postgres` superuser, which writes across 14 schemas
including the quarantined `local_service`. A further ephemeral role scoped to `ps01`
writes would be needed, and that is a genuine mutation window rather than a read.

**Recommendation: the next unit is not `H3D-A1`.** It is a remediation unit closing
`F-GATE-RLS-COUPLING`, `F-CATALOG-PROVENANCE` and `auth.users` measurability, with
its own Codex review, followed by a scoped decision on the write credential. Only
then is `OWNER-CP-H3D-A1` a meaningful checkpoint rather than a rubber stamp over
three known holes.

The Owner may of course override this and authorize `H3D-A1` anyway; that is their
call, and it would be recorded as an Owner override of a controller recommendation
rather than as a clean gate.
