## 3. `PRODUCT_EVENTS_HMAC_SECRET` deep-check

- **Code reads it:** confirmed. `apps/hub-web/server/_core/env.ts:8` (`productEventsHmacSecret: process.env.PRODUCT_EVENTS_HMAC_SECRET ?? ""`) and `apps/hub-web/server/webhooks/productEvents.ts:75` (`verifySignature(rawBody, signatureHeader, ENV.productEventsHmacSecret)`).
- **Absent from `.env.example` and real `.env`:** confirmed by reading `apps/hub-web/.env.example` in full (8 declared vars: `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `SUPABASE_STORAGE_BUCKET`, `OWNER_USER_ID` — no `PRODUCT_EVENTS_HMAC_SECRET`) and by key-name-only extraction from the real `apps/hub-web/.env` (`grep -oE '^[A-Za-z_][A-Za-z0-9_]*=' apps/hub-web/.env | tr -d '='` → the same 7 names, no `PRODUCT_EVENTS_HMAC_SECRET`). No value was read.
- **Actual verification code path traced** (`verifySignature`, `productEvents.ts:37-59`):
  ```
  if (!secret || !signatureHeader) return false;
  ```
  An empty string is falsy in JavaScript. **This means: if `PRODUCT_EVENTS_HMAC_SECRET` is unset (and therefore `ENV.productEventsHmacSecret === ""`), `verifySignature` returns `false` unconditionally, for every request, regardless of what signature header is sent.** `handleProductEventPayload` then returns `401 { error: "invalid signature" }` before ever parsing the body or touching the database (comment at line 65 confirms this ordering, and the code confirms it — the JSON parse and schema validation happen strictly after the `isValid` check).
- **Consequence for forgery:** an unset secret makes the endpoint **fail closed in the specific sense that matters for this question — it cannot be tricked into accepting a forged event.** It does not "accept forged events." It rejects *all* events, forged or legitimate, because no signature can ever satisfy an empty-secret HMAC comparison via this short-circuit. The practical consequence of an unset secret today is that `POST /api/webhooks/product-events` is permanently non-functional (denies every caller), not that it is open to impersonation.
- **Relation to R3 / §3.1's shared-secret prohibition:** R3 and §10 D2 are about a *different* problem — a secret that **is** set and shared across all product emitters, which lets any legitimate holder of that one secret choose any `productSlug` and impersonate any other product's events. That risk is real and independent of whether the secret happens to be unset today; it concerns what happens once someone *does* set `PRODUCT_EVENTS_HMAC_SECRET` and hands the same value to multiple product integrations. The two documents' "Open items for a reviewer" section conflates these somewhat: it frames the unset-secret condition as something that "would be a live security gap on top of the already-known shared-secret problem, R3" without having traced `verifySignature`'s short-circuit logic to check which direction the gap runs. The framing is speculative and appropriately marked `UNVERIFIED` rather than asserted as fact, so it is not a fabricated finding — but it invites the reader to conclude "unset secret → forgery risk," which the code contradicts. This is a **MINOR** finding: the documents did not open `productEvents.ts` (it is not listed in either document's "Verification method" file list) and so reasoned about the security consequence without reading the enforcement code, producing an ambiguous/misleading implication on a security-critical path. It does not change the verdict on the shared-secret problem itself, which is correctly and separately identified via §10 D2/R3.

## Findings summary

- **BLOCKER:** none.
- **MAJOR:** none.
- **MINOR:**
  1. §3 (`PRODUCT_EVENTS_HMAC_SECRET`): the documents did not open `productEvents.ts`'s
     `verifySignature` function, and their "Open items" framing implies an unset secret is an
     exploitable gap without checking which direction the fail-mode runs. Actual code shows the
     opposite: an unset secret fails closed (rejects everything), not open (accepts forgeries). Does
     not affect the separately-and-correctly-identified R3 shared-secret risk.
  2. §5 (inventory completeness): four PawSpace `.env.example` names (`LINE_TARGET_ID`,
     `CAMERA_REQUESTER_IP_HEADER`, `CAMERA_ALLOWED_FEED_HOSTS`, `APP_BASE_URL`) are absent from the
     "26 distinct … inventoried" secret table despite the document including comparable non-secret
     names elsewhere (`OWNER_USER_ID`, `SUPABASE_STORAGE_BUCKET`) for completeness. Inconsistent
     application of the stated inclusion criterion, not a missed credential.
- **OBSERVATION:**
  - PawSpace's `require*` function count is 10, not "~11" as stated — within the stated `~` tolerance,
    noted only for precision.
  - Both documents are unusually disciplined about marking `UNVERIFIED` items with reasons; this made
    independent verification straightforward and is worth naming as a positive, not just an absence of
    problems.

  to hunt for an inline validation check the documents might have missed elsewhere in each repo — I
  verified the specific files and claims the documents named, which is what the brief's deep-checks
  ask for, not an exhaustive re-audit of every file in every product.
- I did not verify Cloudflare token scoping, LIFF fallback behavior, or IAM scope for the Google
  service account — these are correctly marked `UNVERIFIED` by the documents themselves and require
  either a live provider console check (out of scope, no network calls permitted) or information this
  session did not have access to.
- I did not attempt to enumerate every `process.env.*` read across every product's entire codebase to
  build an exhaustive from-scratch inventory; I verified the documents' specific named claims and ran
  targeted greps for common provider names and common `.env.example`/`.env` locations. A slower,
  file-by-file pass could still surface a missed name, though the targeted checks above found nothing
  beyond the four PawSpace names already flagged.

## What I would want re-examined with more time

Whether `PRODUCT_EVENTS_HMAC_SECRET` is actually set today in the Cloudflare Workers secret store
(not locally, where it's confirmed absent) — the documents correctly flag this as unresolved without a
value-bearing check, and it changes the practical urgency of D2's shared-secret remediation: if it's
unset in production too, the webhook receiver is currently dead code in practice (harmless but
non-functional); if it's set only in Cloudflare and equal to some shared value, D2's risk is live today,
not just a future one.
