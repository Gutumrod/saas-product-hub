## 5. Mandatory deep-check 4 — Runtime matrix accuracy

Independently read `package.json`, lockfiles, and `.nvmrc`/`.node-version` for all 8 repositories.

Confirmed accurate: no repository anywhere declares `engines.node` or a `.nvmrc`/`.node-version`
file; PS01 and DC01 both pin `packageManager: "pnpm@11.21.0"` (verified by direct grep of both
`package.json` files); `hub-web`, BK01, CM01 have root `package-lock.json` with no `packageManager`
field; MT01 and HC01 have no root `package.json`, and their `server/package.json` files have neither
field, with `server/package-lock.json` present in both.

**MAJOR discrepancy found — the matrix's exhaustiveness claims for three products are false:**

- **LK01:** RUNTIME_MATRIX.md states *"not applicable — no `package.json` exists anywhere in this
  repository... the directory contains only `docs/`, `docs-pre-sync-...`, `references/`, and
  `vendor/`."* This is factually wrong. `products/WSTERA-Link/vendor/modules/` contains **10**
  `package.json` files (one per vendored module: `audit-log`, `auth-supabase`, `config-runtime`,
  `health-check`, `import-export`, `payment`, `rate-limit`, `subscription`, `tenant-context`,
  `webhook-receiver`), each with its own `package-lock.json`. None declares `packageManager` or
  `engines`, so this does not change the document's ultimate conclusion ("no Node pin anywhere"),
  but a document whose entire premise is "verified directly... nothing inferred" asserted the
  non-existence of files that a single `find products/WSTERA-Link -iname package.json` (10 seconds)
  disproves.
- **MT01:** the matrix states *"The only `package.json` found is nested at `server/package.json`."*
  Also false — `products/multi-tenant-ai/modules/{ai-provider,auth-supabase,enterprise-features,
  payment,subscription,tenant-context,webhook-receiver}/package.json` exist (7 files), none with
  `packageManager`/`engines`.
- **HC01:** same claim, same error — `products/headless-commerce/modules/{file-storage,import-export,
  payment,product-catalog,webhook-receiver}/package.json` exist (5 files), none with
  `packageManager`/`engines`.

The missed files don't declare the fields the matrix is tracking, so the document's **numeric
conclusions** (portfolio Node/package-manager standard, the 5–2 npm/pnpm lockfile count, the
adoption-gap table) are not invalidated by this alone — but the document did not check what it
claimed to check, and its own count of "npm lockfile evidence" is arguably understated (these module
directories also carry `package-lock.json`, uncounted). This is exactly the class of error the
review mandate exists to catch: a confident, falsifiable claim of completeness that is wrong.

**Portfolio standard judgment:** the document's own recommendation (npm as majority, Node 22 as a
maturity-based pin, `packageManager` version pinned to host-installed version) is reasonable and
correctly disclaims §0-prohibited reasoning. The lockfile update policy ("CI runs a frozen install;
falling back to non-frozen is a G1 failure; lockfile always committed; monthly review cadence plus
immediate action on high/critical") is specific enough to encode as a CI check (`npm ci` /
`pnpm install --frozen-lockfile` failing on drift) — **enforceable**, with the caveat that "monthly"
is explicitly flagged by the document itself as a default, not a hard requirement, which is honest
rather than a gap.

**Finding: MAJOR.** Three false "no other package.json exists" / "only X exists" claims. Does not
change the document's final numeric standard or gap table, but must be corrected before this can be
called independently verified, and it undermines confidence in the document's other "verified
directly" claims that I did not personally re-check line-by-line (e.g. exact `pnpm -v`/`node -v`
values on the audit host, which I did not rerun).

## 9. Limitations of this review

- Release-authority search (deep-check 1) was scoped to `*.md` files plus a small set of
  ownership-shaped keywords; non-Markdown files (package.json `author`, LICENSE headers) were not
  checked. Low risk, not exhaustive.
- Casing/stale-reference search (deep-check 3) did not extend into the nested product repos' own
  `docs/` trees, matching the scope the map itself declared (parent-repo only). If P0a item 6's
  document-reconciliation work later needs a nested-repo mixed-case sweep, that is separate work, not
  covered here.
- No installs, builds, or test runs were performed (per hard rules); all findings come from `git`,
  `grep`, `find`, and direct file reads.
- I did not independently rerun the map's claim that a "background" grep for release-authority
  strings "ran past the interactive timeout and finished in the background" — I only confirmed the
  grep's *result* is reproducible now, not the process description of how the implementer originally
  ran it.
- I did not verify every one of the ~20 non-in-scope registry entries' paths against disk beyond the
  ones needed for the scope-conflation finding (item 2 above).

**If I had more time, the one thing I would re-examine:** re-run RUNTIME_MATRIX.md's file-discovery
step with an explicit `find <repo> -iname package.json` per repository (not a manual/spot-check
listing) before trusting any "the only package.json is X" or "no package.json exists" sentence in
any future version of this document — that single class of miss is what turned three of the eight
per-repository rows from verified to overclaimed.
