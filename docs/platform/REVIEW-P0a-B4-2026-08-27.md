## Deep-check 3 — `.gitignore` judgment call

Ruling: **the choice is safe today, but leaves a specific, named, un-remediated failure mode for
later — this is the "safe-only-if-something-else-is-remembered" case, and what must be remembered is
recorded only as a soft "reviewer re-check" note, not as an actionable follow-up tied to the eventual
rename.**

- `git config --get core.ignorecase` on this host returns `true`. On this Windows host, gitignore
  pattern matching is case-insensitive, so **today**, keeping either casing line (or both, or
  neither, so long as one exists) has the same practical effect locally — the choice is genuinely
  inert on this host right now.
- The actual on-disk/on-`origin` directory is still `WSTERA-Link` (mixed-case) — confirmed via
  `ls products/` and `git log --follow` on `.gitignore` (implementer's citation). Keeping the
  mixed-case line and dropping the lowercase duplicate is therefore correct **for today's disk
  state**, and is not a regression on any host, including a hypothetical case-sensitive one — the
  lowercase line never matched the real directory on a case-sensitive filesystem anyway (the
  directory is not, and has never been, `wstera-link`).
- The exposure is forward-looking: §10 D5 makes `products/wstera-link` (lowercase) the canonical
  future path, and the physical rename is explicitly out of this brief's scope, deferred to later
  work. When that rename executes, the *only* remaining `.gitignore` line will be the now-wrong
  mixed-case `/products/WSTERA-Link/`, and on a case-sensitive filesystem (Linux CI, most cloud
  runners) that line will silently stop matching the newly-lowercase directory — the exact "nested
  repo silently becomes untracked in the parent" failure mode the brief warns about. On this Windows
  host (`core.ignorecase=true`) the failure would stay masked even after the rename, making it more
  likely to go unnoticed until it surfaces on a different host or in CI.
- **What must be remembered:** at the moment `products/WSTERA-Link` is physically renamed to
  `products/wstera-link`, `.gitignore` must be updated in the same change (either swap the casing
  back, or carry both lines until the rename is confirmed everywhere). **This is not recorded as an
  explicit action item anywhere** — not in `PHASE_P0a_B4_EVIDENCE.md`'s worklist proper, not as a
  `.gitignore` comment, and not in the master plan's R10 risk row (which mentions "path casing
  all-lowercase (§10 D5)" generically but does not name `.gitignore` specifically). It appears only
  in the evidence doc's own "items reviewers should re-check first" list (#1), framed as "confirm my
  reasoning was right," not as "remember to flip this at rename time."

This is a real, named gap, but it is inert today, was reasoned through explicitly rather than
guessed, and was self-flagged (short of the concrete forward action). I am recording it as **MINOR**,
not a blocker — see findings below.
