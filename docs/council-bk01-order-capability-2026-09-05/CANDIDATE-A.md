## 3. Boundary findings

- B-1. **Booking preserved as appointment authority — verified coherent.** Proposal (F2) assigns appointment date/time, staff availability, schedule, hours/breaks/holidays, duration, collision prevention, and booking deposit rules to Booking and states "Order must not create a second appointment scheduler." Prototype lock items 2–6 (F3) and the code spot-check (F21) confirm: Order-linked Booking only after `READY`, same staff+time authority, cannot bypass/displace existing bookings, separate lifecycles, no auto-completion. This is coherent and enforces single-scheduler authority.
- B-2. **Non-goals correctly scoped — verified.** The non-goals are dual-listed and consistent between proposal (F2) and prototype lock (F3): no inventory/warehouse/ERP/POS/shipping/BOM/routing/worker-workload-optimization, no lift/bay/room/equipment resource scheduling, no generic resource-booking engine, no automatic cross-module payment aggregation, no automatic Booking→Order completion, no claim lifecycle inside BK01. These are additive to — not in conflict with — BK01's locked non-goals (F20 vision; F7 scope).
- B-3. **Capacity must not become a second scheduler — must be locked explicitly in Phase 0B.** Order V1 owns "workshop production calendar, daily production capacity, capacity reservation, earliest/requested/promised ready dates" (F2). If capacity is modeled as time-slot resources, Order silently becomes a second appointment/resource scheduler, which the proposal forbids and the lock excludes (lift/bay/room/equipment). Phase 0B must define capacity granularity (e.g., day-level units per capability) and prohibit time-window resource booking inside Order. (Design requirement, not a defect of the proposal.)
- B-4. **ICP expansion is implicit and undebated.** BK01's locked ICP is single-location hair/barber/beauty/nail appointment shops (F20). "Pre-order / made-to-order businesses" with a production workshop is an adjacent segment (e.g., repair/fabrication shops) that the locked vision does not cover. The proposal never asks for an ICP amendment. Phase 0A must either (a) amend the vision via a dated Owner decision, or (b) constrain Order activation to existing-ICP shops that also sell made-to-order work. Approving Phase 0 without this decision leaves the boundary self-contradictory.
- B-5. **"Workshop" scope undefined.** The proposal uses "workshop production calendar" without defining which shops have workshops, what entities constitute the workshop calendar (closed days? holidays? per-capability calendars?), or how it relates to Booking's existing shop closures/holidays (F20 domain rules). Phase 0B must define workshop calendar semantics and their relationship to existing booking closures — reusing, not duplicating, closure data where applicable.
- B-6. **Order↔Booking link model correctly deferred.** The proposal explicitly defers the many-to-many link model to the formal contract (F2) instead of assuming 1:1. Phase 0B must lock: link cardinality, link lifecycle (create/unlink/cancel), cancellation propagation rules, and that completing a Booking never auto-completes the Order (already locked in F3 item 6).
- B-7. **Order-linked Booking deposit policy is unresolved.** Prototype lock item 7 (F3): Booking deposit policy for Order-linked Booking is "Not configured". BK01's locked deposit state machine (F20 domain rules: hold/awaiting/submitted/verified/rejected/refunded, 15-minute hold expiry) is authoritative for bookings; Order-linked bookings must flow through it unchanged, with an explicit Owner decision on whether installation appointments require deposits (D-7).
- B-8. **Customer identity/access is boundary-safe.** Phone = tenant-local customer matching, not an auth credential; order tracking via an opaque recovery mechanism (F2/F3 item 8) — consistent with BK01's locked customer-cancel/reschedule recovery-token and privacy patterns (F20 PRD FR-LIFE-002, domain rules). No raw capacity exposure to customers (F3 item 9) is correctly locked.
- B-9. **Payment boundary is coherent but must be stated as a hard rule.** Order payment status is separate from order lifecycle (F2) and separate from Booking deposit states. Combined with F12 §5 and F13 (centralized billing-core authoritative), Order V1 must not introduce a payment engine, wallet, or cross-module payment aggregation. Order payment status is a BK01-local state domain.

**Boundary conclusion:** the proposed boundary is coherent and preserves Booking authority; it is approvable at Phase 0 level with D-2 (ICP), B-3 (capacity granularity), and B-5 (workshop semantics) as required Phase 0A/0B decisions.
